# 礦工與伐木工的搜尋和效能驗收

## 可玩的差異

礦工和伐木工現在會續掃自己的工作區。每張需要的工單每次最多檢查 128 格，從村民開始搜尋時所在高度向外展開，依序掃到其他高度。走動也保留本輪進度。大區完整掃過仍找不到目標，隔 100 tick 再輪查；新出現的資源要等游標掃回該格才會被發現。第一次掃完前不顯示「沒有可採礦面／樹木」。已有工單的村民只核對該工單，到了現場仍須通過工具、權限與實際採收檢查。替手供應能力另有獨立的搜尋進度。

一般礦區從範圍內已載入區塊登記的方塊實體挑選熔爐。原站或候選站被土地權限拒絕時會繼續找其他合法工位。

## 功能回歸

25×25 工作區的兩項專服案例讓村民從中心搜尋 12 格外的唯一資源。測試先固定起點，直到正式排程選中遠端目標，再恢復村民的正常移動。礦工走到高一格的石面並取得鵝卵石，伐木工走到樹根取得四根橡木並補種。礦工案例也讓不同工單錯開開始搜尋，等完整掃完並出現缺礦提示才加入石頭。另驗證已記住的近爐受保護後，礦工會改認合法的遠爐。

## 專服負載測量

Minecraft 26.3、Java 25、四個可用處理器、1–2 GiB JVM heap。每版本各用全新專服，測試區固定座標、已載入，工人有固定 UUID、工作位置、個人庫存和工具。單人組是礦工，20 與 50 人組各半是礦工與伐木工，尋爐組全是礦工。效能場景固定工人位置，分別量持續採收身旁資源、全區無目標、目標在密閉房間、以及每 100 tick 拆除並補放熔爐。遠程實際走路由上面的功能回歸驗證。

每組預熱 600 tick，接著採樣 800 tick。整服 p95 是從伺服器 tick 開始回呼至工作排程後的結束回呼所經毫秒。計數器只編入暫存測試 JVM，記錄候選地格、工作站位的原版建路呼叫及尋爐查閱量。舊版尋爐計數單位是地格，新版是已載入區塊中的方塊實體。正常組在測試期間持續補回資源以維持需求。空區與封閉區驗證零產出，封閉區也驗證目標仍在。尋爐組逐人驗證重新認領了指定替換站。

## 重跑

在模組根目錄以專案的 Java 25 執行 Gradle 的 `gametestClasses`，並備好 Loom 的 `runGameTest` 引數檔。修改前保存 `build/classes` 和 `src/main/java` 至同一暫存目錄的 `classes/` 和 `java/`；修改後再編譯。以下兩次執行沿用相同的測試、資源與相依版本。請設定 `JAVA_HOME` 指向該 JDK。

```sh
python3 scripts/resource-search-benchmark/run.py "$baseline"
python3 scripts/resource-search-benchmark/run.py
```

設定 `RESOURCE_BENCH_REVERSE=1` 可改用 50、20、1 人的順序；第二輪也交換兩版的執行順序。每一行 `BENCH` 提供 p95、平均每 tick 檢查數、建路數、尋爐查閱數與採收次數。反向重測另記工人工作排程本身的 p95 並逐筆從庫存扣回一塊鵝卵石或四根橡木，再計為一次採收。
